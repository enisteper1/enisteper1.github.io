Should fields get different BM25 weights?

November 2026 · Updated November 27 · 9 min read

Does a match in a short title deserve more weight than a match in a long description? I tested separate BM25 field indexes on WANDS product search and HotpotQA passage retrieval. Weighting helped WANDS by 3.36 nDCG@10 points over its three-field concatenated baseline. On HotpotQA, the test gain was only 0.30 points, and Recall@100 fell. The same scoring rule produces quite different trade-offs.

Both experiments keep the tokenizer and BM25 settings fixed. Each field gets its own index, and we change how much its score contributes to the final ranking.

With only one nonempty field, as in Quora's text-only BEIR corpus, a positive weight cannot change the ranking. There is no relative field-weight optimization to perform.

The basics

What is a field?

A product is not one text. Each of the 43k furniture products in WANDS has five text fields, and each one says something different about the product.

The name says what the product is. The category is a small, repetitive vocabulary (1,117 distinct terms after stemming) that groups products together, and the class is a two-word product type. The description is ten times longer than the name and mixes the product type with style, material and marketing words. The features are the longest field: a list of key : value attributes such as color, material and style, indexed as they are. WANDS also has ratings and review counts, but those are numbers, not text, so they are excluded from this text-field experiment.

What goes wrong when the fields are concatenated?

BM25 then sees one long document. With all five fields that document is 233 tokens on average, and a query word in the six-word name counts the same as that word anywhere in the description or the attribute list. The document's total length decides the length normalization for every match. The term statistics are mixed too: a word that is rare in names but common in descriptions gets a single IDF. The tokenizer post concatenated only the name, category and description (80 tokens), which is the baseline we compare against below.

What do we do instead?

Each field gets its own BM25 index, with its own IDF and its own average length. A product's score is a weighted sum of the five field scores:

s(q, d) = wname · BM25name + wcat · BM25cat + wdesc · BM25desc + wclass · BM25class + wfeat · BM25feat

This is not BM25F. BM25F combines the weighted term frequencies first and saturates once; here each field saturates on its own and the scores are added. It is the simplest version, and it works on top of any BM25 library.

How were the weights chosen?

Each weight took a value from {0, 1, 2, 4}. Settings that differ only by a common factor rank products the same way, so after removing those there are 781 distinct settings, including every single-field and leave-one-field-out case. We split the 479 queries in half, picked the setting with the best nDCG@10 on one half and scored it on the other, then swapped the halves. Repeating this over 5 random splits gives every query an out-of-fold (OOF) score. To see whether the class and the attributes earn their place, we also tuned on the same splits over the 37 settings that use only the name, category and description. Equal weights and the concatenated text have nothing to tune and are scored on all queries.

nDCG@10 uses graded labels (Exact = 2, Partial = 1), MRR@10 counts only Exact products (queries without any Exact product are excluded from that average), and Recall@10 and Recall@100 count both. nDCG uses gain 2grade − 1; unlabeled products count as irrelevant. Recall is low for every method because many queries have hundreds of relevant products.

Tuned weights over all five fields added 3.4 nDCG points and 3.6 points of Recall@100 over the three-field concatenated text, and the interval stays well above zero. It is not a win for every query: 212 queries improved, 158 got worse and 109 did not change. The other rows explain where the gain comes from.

More text in one document hurts

Gluing all five fields into one document scored 1.6 points below the three-field version, and that interval stays below zero too. Adding class and features nearly triples the document (80 → 233 tokens). This changes length normalization and term statistics together; dilution of name matches is a plausible explanation, but this experiment does not isolate its contribution. The same text that hurts inside one document is harmless, or slightly useful, once it has its own index and a low weight. This is the clearest case for separate fields.

Splitting the fields alone is not enough

Giving all five fields the same weight scored the same as the three-field concatenated text (+0.1, interval −1.7 to +1.9). Equal weights give each field score the same multiplier, but individual matches can still contribute different amounts because each index has its own IDF and length normalization. At equal weight the class even hurts: removing it raises nDCG@10 from 0.686 to 0.691. The gain comes from the next step: counting those fields less.

The weights that won

The most common choice, in 6 of 10 folds, was name 1, category 0.5, and a quarter each for description, class and features. In every fold the name had the highest weight and every other field got a quarter or half of it, except one fold that dropped the features completely. The map below holds the name at 1 and the class and features at 0.25, and shows every combination of category and description. Pick a metric to see how the picture changes.

The best region is clear: category at a quarter to a half of the name, and description at a quarter. Dropping either field completely is worse than keeping it at a low weight, and giving the description or the category the full weight of the name is worse too. These cells are scored on all queries, so they are a map of the space rather than a fair test: the best cell reaches 0.724, while the honest OOF number in the table above is 0.719.

The name carries the search

The name alone scores within 2 points of the three-field concatenated text, from a field of six or seven words. Removing it from the equal-weight setting costs 11.3 points, and removing the description costs 2.0; removing the category, the class or the features costs nothing at equal weight. On their own, the category (0.267) and the class (0.239) are weak and largely repeat each other, which fits their low tuned weights. The features alone reach 0.371: the attributes carry real signal, buried in a lot of noise.

Do the class and the features earn their place?

Barely. Tuning only the name, category and description already gives 0.714, +2.9 points over the baseline, with name 1, category 0.5 and description 0.25 in 7 of 10 folds. Adding the class and the features on top gives another 0.5 points, but that interval runs from −0.2 to +1.1 points, with 166 queries better and 139 worse. That is not a difference we can separate from query sampling. The larger grid also made the tuning less stable: the standard deviation across splits went from 0.0015 to 0.0037. So most of the gain comes from weighting the name, category and description. The two extra fields cost little when they get their own index and a low weight, and they hurt when they are glued into the same document.

MRR went the other way

None of the 781 settings beat the three-field concatenated text on MRR@10. The best one reached 0.704 against 0.707, and the tuned all-field result is 0.695. Field weighting puts more Exact and Partial products into the top 10, which nDCG and recall reward, but the first Exact product often lands a little lower. We tuned for nDCG@10. A system that cares most about the first result would need to tune for that metric and check whether the trade-off still holds.

These examples suggest that reducing description influence can help, although they do not isolate a causal mechanism. Porter stems both olive and oliver to oliv, so George Oliver TV stands, whose descriptions say “tv console”, matched the query on brand and description words. With the description at a quarter weight, products named “console table” move to the top. In outdoor sectional doning (a typo for “dining”), the concatenated text even let an indoor/outdoor rug into the top 3, while the tuned weights kept outdoor sectionals there.

The losses are the same mechanism in reverse. The knobs are named “mushroom knob” and “square knob”; only their descriptions mention bathroom vanities. The vanities have bathroom and vanity in their names, so a strong name match on two words beats a single match on the word that matters, knob. The right answer is right there in the class field, Cabinet and Drawer Knobs against Vanities, and the same holds for Shower & Tub Doors against Interior Doors. But as a low-weighted bag of words, the class cannot outweigh two matching words in the name. A sum of field scores cannot tell which query word is the product type and which is a modifier. Using the class well probably means predicting it from the query and filtering or boosting on it, which is a job for query understanding, not for field weights.

HotpotQA: the passage gets more weight

HotpotQA pairs a short title with a longer passage: about 3 and 44 tokens on average. We keep all 5.23 million documents and compare seven relative weight settings against concatenating title and text.

Weights are chosen on dev queries and fixed before evaluating test queries. Every dev fold, as well as the full dev set, selected title 0.5, text 1. WANDS favored the product name; here passage text gets the larger multiplier.

The test gain is small: nDCG@10 rises from 0.5950 to 0.5980 and MRR@10 from 0.7625 to 0.7657. Recall@10 slips from 0.6231 to 0.6220, and Recall@100 drops from 0.7739 to 0.7583, about 1.56 points. If these results feed a reranker, that loss of candidate coverage may matter more than the small top-rank gain. Equal field weights are worse than concatenation on all four metrics.

The two datasets use different relevance labels, so compare methods within each dataset. The notebook does not report a confidence interval for HotpotQA; the small test gain should not be read as an established improvement.

The takeaway

On WANDS, letting the product name dominate added 3.4 nDCG points with no new model. Equal weights gained nothing meaningful, and concatenating all five fields made search worse.

HotpotQA favored passage text instead: twice the title’s weight. Equal weights made retrieval worse here too, but tuning recovered only a small gain over concatenation: 0.3 nDCG points, with lower recall. Weighting can help, but the useful balance—and how much it pays—depends on the dataset.
